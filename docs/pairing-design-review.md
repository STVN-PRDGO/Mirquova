# Pairing design and implementation record

Reviewed 2026-10-27. The initial sections below record the pre-implementation research and proposal. A pairing implementation now exists and is described later in this document; it has not received an independent security audit or complete cross-platform/device validation. Pairing does not grant file access.

## Source findings

- LocalSend's public protocol documents multicast discovery, a certificate fingerprint and transfer request/approval stages. This supports keeping discovery, identity and per-action permission separate. It does not prove that a name or an advertised fingerprint is independently trustworthy. Source: https://github.com/localsend/protocol (v2.2 README reviewed).
- The RustCrypto spake2 0.4.0 documentation says its implementation has not received an independent third-party security/correctness audit. It also explains that PAKE must be bound to the protected channel. Therefore, a short numeric code plus this crate is not being presented as audited pairing. Source: https://docs.rs/spake2/0.4.0/spake2/ . The crate is not a dependency.
- UUID v4 provides a random process-local announcement identifier. Here it is only a discovery/privacy aid, never a public-key identity, authentication secret or trust pin. Source: https://docs.rs/uuid/1.29.0/uuid/ .
- RFC 2782 permits the 16-bit SRV port range including zero. Our dedicated prototype presence service explicitly uses zero and exposes no application endpoint. That is a local presence convention, not an interoperable transport standard. Source: https://www.rfc-editor.org/rfc/rfc2782.html .

No third-party source code, interface composition or branded asset was copied. REA is not needed to inspect these public specifications and was not installed or invoked.

## Threat model for the current presence feature

Assume another LAN participant can forge names, addresses, TXT metadata and service IDs; replay records; induce collisions; and flood announcements. A LAN is not an authentication boundary. Every candidate remains unverified. The native/Flutter contract rejects transport endpoints in this presence-only version and offers no connect/transfer action.

A user-approved announcement discloses the chosen name and interface addresses on multicast-capable local networks. It contains no account name, OS hostname, file list, key or token. The identifier is random for each app process and never persisted. Hiding cannot erase a name already observed by another device. Scan results are explicitly observations from the last scan, not proof a peer remains online.

Visibility is off by default, capped at 120 seconds including startup, and cancelled on hidden/paused/detached lifecycle events or disposal. Native cleanup unregisters and shuts down on normal exit, failure or unwind. An abrupt process/OS termination cannot guarantee delivery of multicast goodbye packets. Scan result refresh and authenticated liveness must remain separate concerns.

## Initial proposal (pre-implementation)

Evaluate an established TLS 1.3 implementation with OS-backed identity protection and a high-entropy, short-lived QR/bootstrap invitation. The receiver must verify an out-of-band certificate/public-key pin before sending an invitation secret. Never trust a pin learned only from mDNS, silently accept any certificate, or downgrade to cleartext when QUIC is blocked.

A bootstrap invitation would require at least 128 bits of library-generated entropy, explicit host approval, one use, short expiry, bounded attempts, strict message sizes and no URL/log leakage. Peer key enrollment must occur inside the authenticated channel and bind roles, protocol version, invitation and both peer identities. This remains a design candidate requiring a concrete implementation review; QR appearance alone is not authentication.

After enrollment, future sessions must prove possession of the pinned identity using the transport's standard handshake. Windows key material should be protected with an appropriate OS facility; Android should use Keystore-backed protection. SQLite would store trust records/public identity and revocation state, not unprotected private keys. Reinstall/key change/revocation require explicit user handling rather than transparent trust replacement.

A short numeric pairing mode remains deferred until a reviewed PAKE/channel-binding design and suitable implementation are chosen. No home-made key exchange, MAC, cipher, SAS derivation or custom certificate bypass is authorized by this document.

## Original acceptance gates

- Rejected/missing/wrong pin, invalid certificate and downgrade tests.
- Expired/replayed invitation, attempt limiting, role/version mismatch and duplicate enrollment tests.
- Identity storage, restart, key change, revoke and interrupted-enrollment recovery tests on Windows and Android.
- Explicit per-transfer and per-cast consent after pairing; pinned trust never grants filesystem access.
- Two-process and then two-physical-device tests; no live device support claims from fixtures.

The original protocol specification was not supplied. This is an independently derived proposal, not a recovered specification or a security clearance. The current pairing implementation still requires cross-platform and physical-device validation; do not open any file/capture/media service until the remaining gates are satisfied.

## Concrete implementation and remaining evidence

The implementation below now exists in the Rust core and Flutter pairing screen. This records current behavior and its evidence limits; it is not an independent security audit or a claim of supported device combinations.

### Protocol and identity

1. Use TLS 1.3 through Rustls, with its maintained AWS-LC cryptographic provider. Do not add a custom certificate verifier, accept cleartext fallback, or implement ciphers, key exchange, signatures, MACs, or key derivation in application code. Rustls documents standard certificate verification and AWS-LC target support for the project's current Windows, Linux, macOS, Android ARM64, and iOS ARM64 targets. Target builds still need to pass in this repository. Sources: [TLS 1.3 (RFC 8446)](https://www.rfc-editor.org/rfc/rfc8446.html), [Rustls](https://docs.rs/rustls/latest/rustls/), [AWS-LC platform support](https://aws.github.io/aws-lc-rs/platform_support.html).
2. Each installation has a long-lived self-signed **CA identity certificate** (`CA:TRUE`) and private key. Generate it with the maintained `rcgen` crate, then issue separate TLS leaf certificates with the required DNS name and server/client usages. Persist the CA private key only through an OS-backed secret store; fail pairing closed if that store is unavailable. Never put private keys in ordinary preferences, SQLite, logs, backups, invitations, or discovery records. Rustls-WebPKI explicitly warns against using a self-signed end-entity certificate as its own trust anchor, so the QR must carry the public CA certificate bytes and the client must compare their digest with the displayed fingerprint before adding that CA certificate to its root store. Sources: [rcgen](https://docs.rs/rcgen/latest/rcgen/), [Rustls-WebPKI trust-anchor guidance](https://docs.rs/rustls-webpki/latest/src/webpki/trust_anchor.rs.html).
3. Use Flutter Secure Storage as the platform adapter for Windows, macOS, Linux, Android, and iOS. Its documentation lists all five supported platforms; Linux still depends on the host's Secret Service/libsecret availability. The product must surface unavailable storage rather than silently falling back to plaintext. Source: [Flutter Secure Storage](https://pub.dev/packages/flutter_secure_storage).
4. The host starts a temporary TLS listener only after explicit user action. It generates a 256-bit invitation secret from the operating-system CSPRNG and shows a QR code containing invitation v2: private IPv4 endpoint, bounded public identity CA certificate DER, secret, protocol version, purpose, and a maximum 120-second expiry. The fingerprint is computed from the included DER for display and out-of-band comparison; it is not a separate wire field. The payload is at most 2048 bytes. The secret is a bearer invitation, not an identity. It is single-use and server-owned expiry/attempt state is authoritative; the JSON TTL is only a hint.
5. The joining device scans or pastes the invitation, verifies the digest of the included CA certificate, and shows the host name and fingerprint for explicit comparison. It adds that CA certificate as the only root for the TLS connection and verifies the server leaf through the standard Rustls verifier before sending any secret. Pin mismatch, unsupported TLS version, malformed input, expiry, or a failed attempt limit aborts without downgrade.
6. Inside the pinned TLS session, the joining device sends the one-time secret and its public identity CA certificate. The host checks live expiry and attempt state, then accepts a second TLS 1.3 connection with client-certificate authentication, using a trust store scoped only to that submitted CA. The joiner presents a separate client leaf issued by its CA; Rustls verifies the chain and proves possession of the leaf private key. The host confirms the authenticated identity chain ends at the exact candidate CA, then asks its user to approve the identity. Approval atomically consumes the invitation and enrolls the CA certificate. The joiner pins the host CA from the invitation. The enrolled peer record stores CA identity, user-visible name, protocol version, and revocation state; private key material stays in OS-backed storage. A pin learned solely from discovery is never enrolled.
7. Subsequent sessions require TLS 1.3 mutual certificate authentication and the stored peer CA pin. Leaf certificates may rotate under the same enrolled CA. Trust never grants access to files, screen capture, or media; each transfer/cast/share operation needs separate consent. Revocation immediately removes the peer CA pin and any session authorization.

This proposal uses the out-of-band invitation secret to authorize one enrollment and a second, standard mutual-TLS handshake to prove possession of the joining identity key before approval. It does not introduce a numeric-code PAKE or claim that mDNS, a device name, or an unverified candidate is an identity. The scoped trust store must contain only the candidate CA for that pending enrollment, and the host must compare the authenticated chain's root fingerprint to that candidate before presenting approval. Before code is merged, review the client-certificate enrollment and server-owned invitation state machine against replay, concurrent attempts, restart, and revocation cases.

### Platform and evidence boundary

The implementation target should cover the Flutter platforms already present in CI: Windows, Android, Linux, macOS, and iOS. The first end-to-end acceptance pair remains Windows ↔ Android, as required by the roadmap. Every platform must compile the same Rust TLS core and use its native secure-storage backend before it may enable Pair. TV is an Android form factor, not evidence of TV UX support: remote-control navigation, installation, and secure-storage behavior still need a physical TV run. iOS simulator success is a build/test result only and does not prove two-device LAN behavior.

Required tests before calling pairing implemented:

- A v2 invitation's CA certificate digest matches its included DER; valid CA pin and secret succeed; wrong pin never discloses the secret; TLS downgrade and plaintext are rejected.
- Wrong, expired, replayed, consumed, or over-attempt invitation fails; simultaneous use can enroll at most once.
- Host restart invalidates pending invitations; enrolled pins persist; deleted/corrupt secure storage fails closed.
- A mismatched identity, duplicate identity, protocol/role mismatch, and certificate change require explicit handling and never silently replace a pin.
- Revoke prevents the next authenticated session. Pairing alone cannot start a transfer or cast.
- Rust unit tests cover parser and state transitions; cross-platform CI builds cover every target; Windows ↔ Android physical-device tests cover successful pairing, rejection, restart, and revoke. Android TV, iOS physical devices, and other listed platform pairs need separate device evidence.

Dependencies were retrieved with the user's authorization. The implementation uses Rustls 0.23 with AWS-LC, rcgen 0.14, Flutter Secure Storage 11.2, the Dart `qr` encoder 4.0, and `mobile_scanner` 7.4 on Android/iOS/macOS. Windows/Linux use invitation paste. `Cargo.lock`, `pubspec.lock`, and third-party notices are updated. Android declares `allowBackup="false"`; CI now checks the merged APK manifest for this setting, but that check and device-to-device restore behavior still need Android build/runtime results. Linux Secret Service availability and Apple Keychain behavior also need platform checks.

### Implemented slice and outstanding checks

Rust creates a CA identity, validates stored cert/key pairs, issues TLS leaf identities, and runs the bootstrap and mTLS approval exchange. Temporary bearer-secret hex and the generated native invitation payload use zeroizing buffers; the native FFI JSON allocation is wiped when freed. Flutter's displayed QR/copy payload is an immutable Dart string and cannot be guaranteed erased before garbage collection, so the UI drops its reference on expiry, stop, backgrounding, or disposal. The Dart parser also wipes its temporary UTF-8, certificate and secret byte buffers. Identity key copies are cleared on native validation or secure-storage write failures as well as after transport use. Concurrent callers receive independent mutable copies of a single-flight loaded identity, so cancelling an older operation cannot erase the active operation's key. Outbound connection polling observes cancellation and drops an in-progress socket rather than waiting for the full blocking connect timeout. Flutter displays a QR invitation, supports camera scan on plugin platforms and manual paste elsewhere, requires explicit out-of-band fingerprint confirmation on the joining device, and shows the joining certificate fingerprint before host approval. The joining UI clears its invitation and fingerprint confirmation at the parsed TTL; server-owned monotonic expiry remains authoritative. Trusted peer mutations are serialized within the app's repository so a queued revoke is not overwritten by an earlier in-flight trust write. Accepted public peer certificates and aliases are written to secure storage; local revoke removes the record. No app data or files are transferred by pairing.

Verified on the Windows development host: Rust workspace tests, Rust Clippy with warnings denied, Dart analysis, Flutter functional tests, and pairing invitation/identity/trust repository tests. The latest Rust run passed 42 tests with 6 network tests intentionally ignored; all four explicit same-host private-interface transport cases passed. They cover TLS bootstrap, mutual authentication, wrong-secret rejection followed by valid single-use pairing, host approval/rejection, racing joiners sharing one invitation, and replay rejection after a host restart with its identity preserved. TLS tests also reject a TLS-1.2-only client and plaintext data at the TLS-1.3 listener. Unit tests confirm pre-cancelled connect attempts return before opening a socket, cancellation interrupts a pending connection poll, and wrong fingerprints are rejected before connection. The Windows Flutter suite also exercises the Rust FFI wrong-pin and invalid-bind-address paths without opening a listener or peer connection; Android/iOS/macOS/Linux native smoke tests repeat these FFI checks on their actual native libraries when CI runs. Run the transport tests with `MIRQUOVA_PAIRING_TEST_IPV4` set to an available RFC1918 interface. Windows Rust and Android ARM64/x86_64 Rust release builds pass locally after the zeroizing payload changes; the Android ELF machines are AArch64 and x86-64 and both expose the pairing ABI. The Windows GNU target also passes `cargo check`. The Windows and Linux/macOS CI jobs now invoke the same-host transport tests serially; results await a workflow run. The same-host tests exercise one host and are not physical-device validation. [Public Foundation checks run 16](https://github.com/STVN-PRDGO/Mirquova/commit/533a33c3ddb06cffc7e717fb0d3e3d92a2021b6d/checks) failed in the iOS simulator bridge job after 16m56s; that checkout's command had a 600-second subprocess limit. Current workflow changes cap platform jobs at 45 minutes and the iOS test at 10 minutes with stage markers, but a passing rerun is still required. Native builds and secure-storage runtime behavior across all targets, plus physical Windows-to-Android pairing/reject/restart/revoke tests, are still required before enabling later authenticated data sessions.

## Input-validation groundwork

The Rust core includes a [bounded v2 invitation parser](../shared/contracts/pairing-invitation.md) and an OS-CSPRNG-backed invitation payload generator for the independently proposed bootstrap JSON format used by the implemented pairing flow. The parser bounds certificate bytes but does not validate X.509 or calculate its fingerprint; the transport validates the certificate before use and the Flutter UI calculates and displays the out-of-band comparison fingerprint. Tests cover malformed/oversized input, duplicate and unknown fields, unsupported versions/purposes, endpoint restrictions, certificate/secret encoding, whole-second TTL boundaries, generated-secret round trips, borrowed unescaped strings, escaped JSON strings, and diagnostic redaction. The generated invitation deadline starts immediately after secret creation, before payload construction. Server-side state enforces expiry, one-use consumption and bounded attempts; a receiving client's local lifetime alone cannot establish server expiry or replay protection.
